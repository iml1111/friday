## 1. 배경 & 문제

Friday는 **클라우드/서버 사이드에서 에이전트 루프를 구동**하기 위한 SDK다. 그래서 에이전트는 로컬이 아니며, 사용자의 브라우저를 **직접 제어할 수 없다**. 브라우저는 사용자 기기의 익스텐션과 같은 **클라이언트** 쪽에 있다.

따라서 서버 에이전트가 클라이언트와 통신하며 브라우저 제어를 *지시*하고 *결과를 회수*하는 구조가 필요하다. 본 문서는 그 **접근 방식**을 제안한다 — 구현 명세가 아니라 설계 골격과 결정 근거를 기록한다.

---

## 2. 핵심 통찰 — 시임(seam)은 이미 존재한다

답의 절반은 현 구조에 이미 들어 있다.

- `Tool.call(args) -> ToolResult`는 그냥 async 함수다 (`tools/base.py`). 루프(`run_one_turn`)는 도구가 **어디서** 실행되는지 전혀 모른다 — `run_tools`가 `call()`을 await하고 `ToolResult`를 받아 다음 턴에 실어 보낼 뿐이다.
- **와이어 포맷도 이미 있다.** 서버→클라이언트는 직렬화된 `tool_use`(name + input), 클라이언트→서버는 `tool_result`(data + is_error)다. 즉 Friday의 데이터 모델이 **그대로 서버-클라이언트 프로토콜**이 된다.

> **결론**: 브라우저 제어는 "원격 도구" 한 종류를 추가하는 일이다. `call()`이 로컬 실행 대신 익스텐션으로 명령을 내려보내고 결과를 받아오면 된다. 루프·오케스트레이터·상태 전이 구조는 **무수정**.

## 3. 설계 원칙

**SDK 밖 호스트 레이어로 둔다.** while-true 드라이버를 호출자에게 외부화했듯([00-overview](../architecture/00-overview.md) 참조), 브라우저 브릿지도 `friday_agent/core`가 아니라 **호스트 측 레이어**(BYO 도구 + 트랜스포트)로 산다.

이것은 SDK *변경*이 아니라 SDK *응용*이며, 구현 스코프 헌장과 정합한다 — core 루프는 도구가 원격인지 끝까지 모른다.

## 4. 핵심 결정

| 결정 | 선택 | 근거 | 기각안 |
|---|---|---|---|

## 5. 아키텍처 개요

### 배치

| 조각 | 사는 곳 | 정체 |
|---|---|---|
| 브라우저 `Tool`들 | 호스트 (BYO 도구) | `tools/base.py` 확장점 그대로 — `call()`이 원격으로 나감 |
| `RemoteBrowserBridge` + WS 서버 | 호스트 프로세스 | 세션 레지스트리 · pending future · 명령 라우팅 |
| 익스텐션 | 클라이언트 | WS 클라이언트 + Dispatcher (CDP 매핑 + 배치 실행 + 매크로) |

`friday_agent/`는 그대로다.

### 데이터 흐름 (단일 명령 왕복, 입도 A)

```
LLM ──tool_use(browser_click,{ref})──► run_one_turn → run_tools → ClickTool.call(args)
                                                                            │
                                                              RemoteBrowserBridge
                                                                │ corr_id 발급 + Future 등록
                                                                │ registry[session_id] → conn
                                                                ▼
                         WS  {id, op:"click", params} ─────────────────────► Extension
                                                                              │ Dispatcher
                                                                              │ chrome.debugger(CDP)
                                                                              │  → Input.dispatchMouseEvent
                         WS  {id, ok:true, data} ◄──────────────────────────  실행 결과
                                                                │
                              Future.set_result(data) → ToolResult(data)
                                                                ▼
                              tool_result Message  (par-critical 쌍 유지) → 다음 턴
```

**배치 변형(입도 C)**: `browser_run_steps([navigate, wait_for, type, click])` — tool_use 1개 = WS 프레임 1개 = 원시 N개 리스트. 익스텐션이 순차 실행 후 **집계 결과 1개**를 회신한다(중단 규칙은 §8.4). 흐름은 위와 동일하되 op가 리스트이고 결과가 집계라는 점만 다르다. par-critical은 1쌍 유지(서브결과 N개).

동기-await 모델이므로 `call()`은 corr_id 키 future를 timeout과 함께 기다린다. 별도 suspend sentinel·루프 수정이 필요 없다.

## 7. 도구 표면

도구는 네 갈래이며, **명령 입도(A/C)와 직교**한다.

### 7.1 입도 — A / C / 매크로

| | 전송 단위 | 시퀀스 지능이 사는 곳 | LLM 관여 |
|---|---|---|---|
| **A. 스텝와이즈 원시** | tool_use 1 = WS 1 = 원시 1 | **LLM** (매 턴) | 매 스텝 |
| **C. 서버 조립 배치** | tool_use 1 = WS 1 = 원시 **N개 리스트** | **에이전트** (즉석 조립 → 데이터로 전송) | 배치 시작 1회 |
| B. 매크로 | tool_use 1 = WS 1 = 이름 1 | **클라이언트** (내장) | 이름 호출 1회 |

> **C는 A를 미리 보낸 것일 뿐이다.** 클라이언트 실행기는 동일하고, C에 새로 필요한 건 (1) 리스트를 받는 도구, (2) 순차 실행·집계뿐. 즉 A가 토대고 C는 그 위에 얹는 얇은 배치 도구다. 매크로(B)는 시퀀스가 클라이언트에 *내장*된 별개의 것 — "배치 = 매크로"가 아니다.

### 7.2 관찰 도구 (A의 토대)

실시간으로 변하는 페이지에 강건히 상호작용하려면 에이전트가 **현재 상태를 읽을 수 있어야** 한다. `act → read → adapt` 루프의 토대다.

- `browser_read` — 현재 페이지 구조를 서버로 전달 (표현 형식은 §8.1).
- `browser_screenshot` — 비전 모델 보완(좌표 기반).

### 7.3 원시 액션 도구

- `browser_navigate · click · type · evaluate …`
- **ref 기반 타겟팅 권장**: 관찰(§8.1)이 부여한 요소 ref를 받아 brittle한 CSS 셀렉터를 피한다. 동적 페이지에서 타겟 안정성↑, stale-ref 감지(§8.3) 가능. (대안=셀렉터, 단순하나 취약.)
- **동시성**: 단일 탭에선 거의 전부 순차여야 한다(읽기도 변경과 레이스 위험). `is_concurrency_safe` 보수적 기본값 `False`가 이미 옳게 동작하므로 그대로 둔다 ([02-tool-orchestration](../architecture/02-tool-orchestration.md)).

### 7.4 배치 도구 (입도 C)

- `browser_run_steps([...])` — 결정적·예측 가능한 시퀀스용. 익스텐션이 순차 실행·집계. 중단·가드 규칙은 §8.4.

### 7.5 매크로 (소수)

- `browser_fill_form · browser_extract · browser_wait_for …` — 단계가 익스텐션에 *내장*된 클라이언트 루틴. 흔한 흐름의 턴 수 절약.

## 8. 관찰 & 결과 해석

A의 강점(동적 웹 적응)과 직결되는 절. **무엇을 관찰로 보내고, 결과가 기대와 어긋날 때 어떻게 대응하는가**를 다룬다.

### 8.1 관찰 표현

- **기본 = 의미 기반 스냅샷** — 접근성 트리(CDP `Accessibility.getFullAXTree`) 또는 정리된 DOM(script/style/비가시 요소 제거), **상호작용 요소에 안정적 ref 부여**. 작고 LLM 친화적이며 "현재 페이지 상태 전달"이라는 목적을 달성한다.
- **raw HTML은 옵션**(`format:"html"`) — 진짜 원본이 필요할 때만. 현대 페이지의 raw HTML은 수백 KB\~MB라 **컨텍스트 윈도우를 즉시 압박**한다 → 서브트리/뷰포트 스코프 필수 ([04-context-compaction](../architecture/04-context-compaction.md) 연결).
- **ref ↔ 액션 결합** — 관찰이 요소에 ref를 부여하면 `click/type`이 ref를 받아 셀렉터 brittleness를 피하고, 아래 stale-ref 감지가 가능해진다.

### 8.2 결과 세 클래스

| 클래스 | 의미 | 처리 |
|---|---|---|
| ① 기대대로 성공 | op 완료, 상태가 기대와 일치 | 다음 단계 진행 |
| ② **성공했으나 예상 외** | 전송·실행은 됐지만 관찰 상태가 발산 (예상 못 한 내비게이션·모달·캡차·쿠키배너·검증 에러·무효과) | **§8.3** |
| ③ 전송/실행 실패 | timeout·단절·op 예외 | 전송 계층, §11 |

②가 "성공인데 놀라운" 케이스라 놓치기 쉽다 — 본 절의 초점.

### 8.3 예상 외(②) 처리 — 에이전트가 곧 핸들러

예상 외 결과는 **새 제어 구문이 아니라 `tool_result`에 담긴 정보**다. LLM이 다음 턴에 읽고 재계획하며, 루프가 이미 이를 지원한다(tool_result → 다음 턴 → 적응). 따라서 설계 요구는 "**결과를 충분히 관찰 가능하게** 만들어 LLM이 발산을 감지하게 하기"로 환원된다. 두 축:

1. **풍부한 결과 페이로드** — 변경 op는 실행 후 신호(새 URL · 내비게이션 발생? · 새 다이얼로그? · DOM 크게 변함?)를 함께 반환한다 → 부작용에 눈멀지 않음. (또는 A의 `act → read` 재관찰 규율로 보완.)
2. **stale ref / 요소 없음을 타입화된 회복 가능 결과로** — 이전 스냅샷의 ref가 현 DOM과 안 맞으면, 클라이언트는 *조용히 엉뚱한 요소를 클릭하지 말고* "ref stale" 결과를 회신한다 → 에이전트가 재관찰. correctness·safety의 핵심.

### 8.4 C 배치의 예상 외 처리

배치 중 에이전트는 실명하므로 ②가 더 위험하다. 배치 실행기는:

- **첫 예상 외에서 멈춘다**(plow-ahead 금지). 중단 조건 = op 실패 / ref stale / 예상 못 한 내비게이션 / 다이얼로그 출현.
- `{completed:[…], stopped_at:k, reason, observation_at_stop}`를 회신 — **멈춘 지점의 스냅샷 포함** → 에이전트가 *실제 상태*에서 재계획.
- (옵션) **가드 배치** — 스텝마다 기대(예: URL 매칭, 셀렉터 출현)를 실어 클라이언트가 발산을 LLM 없이 감지하고 빠르게 bail. C의 실명을 완화하는 중간 지대.

## 9. 클라이언트 실행 메커니즘

- **추천: 원시 op를 `chrome.debugger`(CDP)로 매핑** — 진짜 입력 이벤트·`Runtime.evaluate`·`Page.captureScreenshot`·accessibility 트리까지 computer-use급 표면을 얻는다. 관찰 ref도 AX 트리/DOM 노드에서 부여한다. 대가는 "디버깅 중" 배너와 `debugger` 권한.
- **혼합 가능**: 싼 DOM 읽기는 content-script, 입력·eval·스크린샷은 CDP. 매크로는 원시를 합성하는 익스텐션 JS 루틴.

## 10. 세션 라우팅 & 트랜스포트

- **익스텐션이 서버로 영속 WS를 먼저 건다.** 익스텐션은 NAT 뒤라 inbound를 받지 못하므로, 클라이언트 발신이 유일하게 성립하는 방향이다. 서버는 그 소켓으로 명령을 내려보내고 결과 프레임이 같은 소켓으로 올라온다 (JSON-RPC-over-WS 패턴).
- **레지스트리**: `session_id ↔ connection` 바인딩. 에이전트는 자신의 session_id로 연결을 조회한다.
- **상관(correlation)**: 명령마다 `corr_id`를 실어 `corr_id ↔ Future`로 응답을 맞춘다.
- **핸드셰이크**: 연결 시 사용자 토큰으로 인증 후 세션 바인딩. (상세는 미해결 — §14)

## 11. 정합성 & 전송 실패 (par-critical)

네트워크는 불안정하므로 단절·타임아웃을 **정상 경로**로 취급한다. *(본 절은 **전송 계층** 실패다. 전송·실행은 성공했으나 관찰 상태가 어긋난 **관찰적 예상 외**는 §8.3이 다룬다 — 두 계층은 구분된다.)*

- **par-critical은 거의 공짜로 보존된다**: `call()`이 *어떤* `ToolResult`든 반환하기만 하면 `run_tools`가 `tool_use`↔`tool_result` 쌍을 맞춘다. 예외가 새어도 오케스트레이터가 잡고 `yield_missing_tool_result_blocks`(`core/loop.py`)가 백필한다 ([06-invariants](../architecture/06-invariants.md)). 따라서 브릿지의 유일한 의무는 **영원히 멈추지 않고, 모든 실패를 에러 `ToolResult`로 변환**하는 것이다.
- timeout → `ToolResult(is_error=True)`, 단절 → pending future reject → 에러 결과.
- **멱등성 함정**: 서버가 timeout으로 포기했더라도 클라이언트는 명령을 끝냈을 수 있다 → 변경 op 재시도 시 **중복 실행** 위험. 완화: 클라이언트 corr_id 디둡, 변경 op는 non-retryable 표시.

---

## 12. 보안 경계

익스텐션은 사용자의 **로그인된** 브라우저에서 서버 명령을 실행한다 — 1급 신뢰 표면이다.

- **확인 게이트**: 변경성 액션(submit·결제·전송)은 익스텐션 UI 승인 또는 op/origin 화이트리스트를 거친다.
- **origin 스코핑**: 에이전트가 구동할 수 있는 사이트를 제한한다.
- 이는 호스트 정책이며 core 루프의 관심사가 아니다.

## 14. 미해결 질문

- **관찰 표현 튜닝**: 접근성 트리 vs 정리된 DOM, 스코프 기본값, 요소 ref의 수명·재사용 정책.
- **"예상 외" 판정**: 무엇을 surprise/배치 중단 조건으로 볼지의 구체 규칙(내비게이션·다이얼로그·무효과 등).
- **가드 배치 기대 언어**: 어디까지 표현을 허용할지(선형 가드 vs 분기·반복).
- **인증·페어링**: 익스텐션 ↔ 세션 바인딩의 구체 핸드셰이크(토큰 발급·검증·만료).
- **멱등성 정책**: 변경 op의 재시도 규칙, 클라이언트 디둡 보존 기간.
- **매크로 카탈로그**: 어떤 흐름을 매크로로 승격할지 기준과 초기 목록.
- **다중 탭/다중 브라우저**: 한 세션이 여러 탭을 다룰 때의 라우팅·동시성.
- **suspend/resume 이행 조건**: 스테이트풀 서버가 한계에 닿는 시점(장시간 액션·수평 확장·재시작 내구성 요구)에 도구 경계 중단·재개 모델로 넘어가는 트리거.
